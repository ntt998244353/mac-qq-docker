## Result: PATCH FIXES THE 16KiB BUG, BUT VENUS STILL UNUSABLE

### 16 KiB alignment bug — FIXED (verified empirically)
Host trace (krunkit --krun-log-level 5, libkrun 1.19.6) shows the blob mappings
now use 16 KiB-aligned sizes and SUCCEED:
    virtio_gpu] mapping: map_ptr=103c30000, guest_addr=280000000, size=147456
    vstate]    add_mapping: host_addr=103c30000, guest_addr=280000000, len=147456   <- OK
    virtio_gpu] mapping: map_ptr=108674000, guest_addr=280024000, size=1048576
    vstate]    add_mapping: host_addr=108674000, guest_addr=280024000, len=1048576  <- OK
    147456 = 9 x 16384  (previously 135168 = 33 x 4096, misaligned -> hv_vm_map EINVAL)
    ZERO 'vstate] Error adding/removing memory map' lines in this run
    (before the patch there were 11 MemoryMap / 11 MemoryUnmap failures per test run)

### Progress vs. unpatched
    unpatched:  vkCreateInstance -> VK_ERROR_OUT_OF_HOST_MEMORY
                host: 'response 0x1200 (command 0x208/0x209)' ERR_UNSPEC
                host: MemoryMap/MemoryUnmap errors
    patched:    vkCreateInstance -> VK_SUCCESS (0)
                host: all mappings clean, no ERR_UNSPEC
                wire-format / protocol-version negotiation completes
                (MESA-VIRTIO: wire format version 1, VK_MESA_venus_protocol spec v1)

### Remaining blocker (NEW, distinct from issue #114)
    vkEnumeratePhysicalDevices(count) = -3  (VK_ERROR_INITIALIZATION_FAILED), n=0
    - Failure is entirely in GUEST USERSPACE at the ring call
      vn_call_vkEnumeratePhysicalDeviceGroups(); guest dmesg is SILENT
      (no virtio_gpu errors) -> not a transport problem.
    - Host-side: libkrun trace shows NO error. rutabaga did NOT emit
      "Failed to create virtio_gpu backend ... Falling back to safe defaults",
      so the GPU backend was created as requested.
    - virglrenderer never logs anything: VIRGL_LOG_FILE=/tmp/virgl-venus.log
      (with VIRGL_LOG_LEVEL=debug) is NEVER created -> virgl_log_init() never runs
      -> the host Venus renderer's vkr_* context path is not reached, meaning the
      host Vulkan present in virglrenderer does not answer the
      vkEnumeratePhysicalDeviceGroups request.
    - CONCLUSION: the host-side Venus implementation in
      virglrenderer-krun 0.10.4e does not successfully serve physical-device
      enumeration over the Venus wire protocol on macOS/MoltenVK.
      This is a SECOND, independent upstream defect: issue #114's 16 KiB
      alignment was necessary but is NOT sufficient.

## Verdict
    krunkit's virtio-gpu delivers Venus/Vulkan-only (VIRGLRENDERER_VENUS |
    VIRGLRENDERER_NO_VIRGL), KMS is disabled (no display scanout), and there is no
    Rosetta. Even after fixing the 16 KiB alignment bug with a patched guest Mesa,
    the host-side Venus renderer cannot complete physical-device enumeration, so
    Vulkan is still unusable. Moving Linux QQ to krunkit therefore yields NO GPU
    benefit today; the currently-working cocoa-way + software-GL path remains the
    right choice.
